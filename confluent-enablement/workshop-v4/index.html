Fundamentals · 2-Min Primer

What are Terraform, Kafka, Flink & Confluent?

Four technologies power this workshop. Here's what each one does in plain English — and how they fit together.

⚙️ Terraform (The Builder)
What it is: Infrastructure as Code (IaC).
Analogy: A robot architect. Instead of clicking 50 buttons in a web console, you write a text file describing what cloud resources you need and Terraform provisions them all automatically — and tears them all down with one command.
📬 Apache Kafka (The Real-Time Highway)
What it is: A distributed streaming event log.
Analogy: A never-ending conveyor belt for data. Applications publish events (e.g. "Player A just bet $500") into categories called topics. Any number of consumers can read those events in real time without the publisher knowing.
⚡ Apache Flink (The Live Brain)
What it is: A real-time stream processing engine.
Analogy: A referee watching the conveyor belt. Flink runs SQL continuously on moving data — e.g. "count bets per player per minute" — and emits aggregated results instantly, before data ever lands in a database.
☁️ Confluent Cloud (The Managed Platform)
What it is: Fully managed Kafka + Flink in the cloud.
Analogy: The stadium that houses the conveyor belt and the referee. Confluent runs Kafka, Flink SQL, Schema Registry, and AI Context (RTCE) so you never manage servers.
💡
How they work together today: Terraform deploys Confluent Cloud. Casino bets flow into Kafka topics. Flink SQL detects anomalies in real time. IBM Bob + AI Agents query the stream and take action.

Understand the Flink Detection Job Before It Deploys

Terraform will deploy this Flink SQL in Module 1. Reading it first means you'll understand exactly what's running in the cloud — not just that something is running.

The Risk Detection Query
INSERT INTO player_risk_alerts
SELECT
  player_id,
  CAST(window_start AS TIMESTAMP(3)) AS window_start,
  CAST(window_end   AS TIMESTAMP(3)) AS window_end,
  COUNT(*) AS bet_count,
  SUM(amount) AS total_wagered,
  AVG(amount) AS avg_bet,
  (COUNT(*) > 20 OR SUM(amount) > 10000) AS is_flagged
FROM TUMBLE(
  TABLE player_events,
  DESCRIPTOR($rowtime), -- Confluent's built-in row-time
  INTERVAL '1' MINUTE
)
GROUP BY window_start, window_end, player_id;
🟣 Prompt Bob in Module 3
SQL Analysis
Explain the Flink SQL statements in 03-flink/. Specifically, explain why we use $rowtime, why TUMBLE window requires DISTRIBUTED BY HASH(player_id), and how the 1-minute tumbling window flags players with over 20 bets or over $10,000 wagered.
Three Things to Understand Now
⏱ Why $rowtime?
Flink needs a time column to define windows. $rowtime is Confluent's built-in row-time attribute — always the right type, always monotonically increasing. PROCTIME() is not supported in Confluent Cloud.
🔀 Why HASH(player_id)?
DISTRIBUTED BY HASH(player_id) routes all bets from the same player to the same partition — but keeps player_id as a normal queryable value column. DISTRIBUTED BY (player_id) would make it a Kafka key, breaking GROUP BY in the TUMBLE output.
🪟 What is a tumbling window?
A fixed, non-overlapping time bucket. Every 60 seconds, Flink seals the current bucket and computes aggregates. One row is written to player_risk_alerts per player per window — with is_flagged=true if thresholds were exceeded.

Enable RTCE — The AI Context Layer for Module 5

RTCE (Real-Time Context Engine) turns your Kafka topics into a live, AI-queryable context window. It's how the watsonx Orchestrate agent in Module 5 reads the risk stream — without writing a single Kafka consumer. Confluent doesn't yet expose RTCE in Terraform, so this one step is manual.

5 Steps in Confluent Cloud UI
  • 1
    Open your cluster (workshop-yourname) in confluent.cloud
  • 2
    In the left sidebar, find and click RTCE (Real-Time Context Engine)
  • 3
    Click Enable RTCE
  • 4
    Click Add Topics → select player_events and player_risk_alerts → Save
  • 5
    Copy the MCP Endpoint URL shown on the RTCE page — you'll need it for Module 5
💡
RTCE exposes your topics as an MCP (Model Context Protocol) server. Any AI agent that speaks MCP can query your live Kafka data as natural-language context — no Kafka SDK needed.
